# oxo-flow AI Evaluation Benchmark

Quantitative evaluation of oxo-flow's AI surfaces at three levels:
**single tool** (knowledge grounding), **single rule** (one-step
generation), and **whole workflow** (end-to-end pipeline generation).

The design follows issue #167's conclusion: instead of adopting an
external MCQ benchmark, the judge is oxo-flow's own fresh knowledge base
plus its own validators (`validate`, `lint`) — a closed loop an external
benchmark cannot provide.

## Layout

```
eval/
  schema.md               # gold CSV column contracts
  gold/
    tool.csv              # tool-layer items (generated, see below)
    rule.csv              # rule-layer items (drafted from real workflows)
    workflow.csv          # workflow-layer items (drafted from real workflows)
  scripts/
    gen_tool_csv.py       # regenerate tool.csv from the embedded knowledge base
    capture_tool.py       # tool layer: prompt the AI per item -> answers.csv
    capture_workflow.py   # rule/workflow layers: generate .oxoflow files
    runner.py             # judge captures against gold -> results.csv
    common.py             # shared stdlib helpers
```

## The loop

```
gold CSVs (draft) ── review by humans ──> approved rows
                                              │
capture_tool.py / capture_workflow.py ────────┘  (AI output per approved row)
                                              │
runner.py ────────────────────────────────────┘  (auto judges -> results.csv)
```

1. **Capture** — run the AI surface against each approved gold row:
   - tool layer: `python3 eval/scripts/capture_tool.py --out outputs/tool_answers.csv`
   - rule layer: `python3 eval/scripts/capture_workflow.py rule --out outputs/rules`
   - workflow layer: `python3 eval/scripts/capture_workflow.py workflow --out outputs/workflows --oxo-flow target/debug/oxo-flow`
2. **Judge** — `python3 eval/scripts/runner.py <layer> --captures <dir-or-csv> [--oxo-flow target/debug/oxo-flow]`
   produces `eval/results.csv` with per-item sub-scores (0..1) and an
   `overall` mean.
3. **Review disagreements** — every judge is deterministic and documented
   in `runner.py`; a human should spot-check rows with low scores (both
   "AI wrong" and "gold wrong" are possible findings).

## The gold set and human review

`tool.csv` is generated by `gen_tool_csv.py` (deterministic, fixed-stride
sampling, curated purpose/alias/negative tables). `rule.csv` and
`workflow.csv` are drafted from real workflows: the 16-file gallery and
the oxo-flow-community repositories. Every row carries a `provenance_url`
pointing at the primary source (bioconda recipe, nf-core module, vendor
page, or the reference workflow file).

Rows start at `review_status = draft` and are skipped by capture/runner
until a human reviewer approves them (see the review workflow in
`schema.md`). `--include-unreviewed` overrides this for previewing.

## What each layer measures

| Layer | Metrics (sub-scores) |
|---|---|
| tool | `name_match`, `version_match`, `no_hallucination` (negative samples) |
| rule | `tool_present`, `version_pinned` (must be a real version: the gold reference pin or one the KB/gallery envs attest), `key_params`, `io_declared`, `validate_pass`, `resources_ok` |
| workflow | `validate_pass`, `lint_pass`, `step_coverage`, `tool_coverage`, `edge_coverage`, `output_coverage` |

The deterministic grounding half of the tool layer is additionally
guarded in CI by `crates/oxo-flow-ai/tests/knowledge_grounding.rs`
(well-known tools resolve with plausible versions, fake tools resolve to
nothing, purpose-word searches surface the right tool) — no API key
required, runs on every push.

## Provider resolution

Capture scripts resolve the AI provider exactly like the CLI:
`OXO_FLOW_AI_PROVIDER` + `<KIND>_API_KEY` env vars, falling back to
`~/.oxo-flow/ai_config.json` (`provider`/`api_key`/`api_url`/`model`
keys). No keys are stored in this repository.

## Regenerating tool.csv after a knowledge refresh

```bash
python3 eval/scripts/gen_tool_csv.py
```

The script pulls versions and dates from the embedded knowledge base, so
a refreshed knowledge base produces an updated gold set — and the diff
between the old and new CSV is itself a record of what the refresh
changed.
