# oxo-flow provenance

Verify output file integrity using stored checksums, and compare the
recorded output checksums of two checkpoints.

## Usage

```
oxo-flow provenance verify [OPTIONS] <CHECKPOINT_PATH>
oxo-flow provenance diff [OPTIONS] <LEFT_CHECKPOINT> <RIGHT_CHECKPOINT>
```

## Description

Re-computes SHA-256 checksums of output files and compares them against
previously recorded values stored in a checkpoint (generated by
`oxo-flow run --provenance`). Reports any mismatches, missing files,
or unverified outputs.

The header also surfaces the workflow provenance recorded at run start —
the git HEAD SHA of the repository the workflow lives in, a content digest
(`sha256:<hex>` of the top-level workflow file as read at run start), and a
marker for whether the workflow file had uncommitted changes — so every
verification names the exact workflow version that produced the results
(see [Workflow Versioning](../reference/versioning.md)). The content hash
covers only the top-level workflow file; for `[[include]]` workflows the
identity is that file plus the separately recorded include resolutions
(`include_resolutions`, their per-include checkout SHAs — see
[Workflow Versioning](../reference/versioning.md)). When the file was
dirty at run start, the content hash is the authoritative record of which
bytes executed: the HEAD SHA alone cannot tell two runs of the same
uncommitted file apart.

The content digest is also **verified**, not just recorded (issue #1350):
verify re-hashes the workflow file named in the checkpoint and compares it
with the recorded digest. A workflow edited after the run is a
verification finding — `✗ workflow content check: workflow changed since
the run …` and exit code 1, exactly like a drifted output checksum. A
workflow missing or unreadable at its recorded path (e.g. a relocated
checkpoint) is reported as unverifiable without failing, so the
output-checksum audit stays usable. Two runs of the same file invoked with
different `--arg` overrides share the raw digest but never the
override-aware `workflow_resolved_hash` fingerprint also stored in the
checkpoint — a run-to-run identity label (see
[Workflow Versioning](../reference/versioning.md)). The same fields appear
in the `--json` `verify` document (`workflow_git_sha`,
`workflow_content_hash`, `workflow_resolved_hash`, `workflow_content_check`
with `status` `matched`/`changed`/`unverifiable`, `workflow_git_dirty`).

A workflow with a metadata table or a `[workflow.metadata_schema]` contract
also records a **canonical metadata digest** (issue #1368):
`sha256:<hex>` over the resolved typed schema plus the effective metadata
rows, with rows sorted by id, columns by name, values trimmed, and empty
values omitted. It is byte-stable across TSV/CSV/JSON sources carrying the
same logical rows and across input row order, so it names *which* typed
table the run consumed (and it is folded into `workflow_resolved_hash`).
Verify reports it as `metadata_digest` (human: `• metadata digest: …`;
absent for legacy checkpoints and contract-free workflows) but does **not**
re-hash the metadata file: re-deriving it needs the exact loaded table
bytes, which the checkpoint does not store — the digest is a recorded
identity, like `workflow_resolved_hash`, not a re-verified claim.

This is essential for reproducible, auditable analysis.

## Options

| Option | Description |
|--------|-------------|
| `-v, --verbose` | Enable verbose (debug-level) logging |
| `--quiet` | Suppress informational output — the version banner is omitted; the verification report, errors, and warnings are unaffected (verified: output is byte-identical with `--quiet`) |
| `--no-color` | Disable colored output |
| `--json` | Output machine-readable JSON to stdout |

## Examples

```bash
# Generate a provenance-tracked run
oxo-flow run workflow.oxoflow --provenance

# Verify output integrity
oxo-flow provenance verify .oxo-flow/checkpoint.json
```

```
  ✓ output/sample2.vcf sha256:def456...
  ✗ output/report.html (expected: sha256:xxx, actual: sha256:yyy)
  ✓ .oxo-flow/chunks/chr/chr1.g.vcf.gz sha256:ccc... (cleaned by design)

```

## Notes

- Runs inside a git repository record the workflow's HEAD commit SHA in
  the checkpoint; `verify` prints it next to the workflow path so each
  result set is auditable to its workflow version. Runs outside a git
  repository omit the line — the field is simply absent.
- Checksums are stored only when `--provenance` is passed to `oxo-flow run`.
- File checksums use streaming I/O (64KB buffer) to handle large files
  (BAM, FASTQ >100GB) without excessive memory usage.
- Mismatches and missing files exit with code 1 (useful for CI/CD
  pipelines).
- A workflow file whose bytes no longer match the recorded
  `workflow_content_hash` also exits with code 1 (issue #1350): the
  digest is re-checked on every verify path, checksum coverage or not. An
  unverifiable file (missing/unreadable at its recorded path) is reported
  without failing — the output-checksum audit stays usable on relocated
  checkpoints.
- Output paths are resolved against the checkpoint's recorded `workdir`
  (the directory the run executed in), not the checkpoint's own
  directory — so the checkpoint can live anywhere (e.g. `.oxo-flow/` on
  the run host while outputs are read from the recorded run directory).
  For legacy checkpoints without a `workdir` field, the checkpoint's
  parent directory is used.
- Transform chunk intermediates deleted by `transform.cleanup = true`
  at the end of a successful run are recorded under `cleaned_checksums`
  and reported as `cleaned (by design)` — they are excluded from the
  missing/mismatched counts and never fail verification. The cleaned
  count appears in the summary only when the checkpoint has any.
  Checkpoints written by releases ≤ 0.17.1 record chunks under
  `checksums` and still report them missing after cleanup — the
  distinction exists only in checkpoints written by newer binaries.

### Verify without stored checksums

When the checkpoint contains no checksums (the run was executed without
`--provenance`), `verify` **degrades to a status summary**: it prints a
note explaining that checksum tracking was not enabled and lists the
completed rules from the checkpoint, then exits with code 0. This keeps
`provenance verify` safe to run on any checkpoint while signaling clearly
that integrity was not verified. The workflow content check (issue #1350)
is the one exception: it runs on this path too, and a workflow whose bytes
no longer match the recorded digest still exits with code 1.

```
Provenance Verify .oxo-flow/checkpoint.json

  Note: No stored checksums found. Run workflow with --provenance to enable tracking.
  Found completed rules: 3
  ✓ align
  ✓ sort_bam
  ✓ trim_reads

  Hint: To verify integrity, provide a checksums file.
```

To get real integrity verification, re-run with `--provenance`.

## JSON output

With `--json`, the verification document is written to stdout (stdout
carries nothing else):

```
{
  "command": "provenance",
  "verify": {
    "checkpoint": "/path/to/.oxo-flow/checkpoint.json",
    "matched": 2,
    "mismatched": 1,
    "missing": 0,
    "cleaned": 1,
    "entries": [
      {"file": "output/sample1.vcf", "status": "matched", "expected": "sha256:abc123...", "actual": "sha256:abc123..."},
      {"file": "output/report.html", "status": "mismatched", "expected": "sha256:xxx", "actual": "sha256:yyy"},
      {"file": ".oxo-flow/chunks/chr/chr1.g.vcf.gz", "status": "cleaned", "expected": "sha256:ccc..."}
    ],
    "workflow_content_hash": "sha256:e3b0c442...",
    "workflow_resolved_hash": "sha256:9f86d081...",
    "metadata_digest": "sha256:6b1d3c7f...",
    "workflow_content_check": {"status": "matched", "recorded": "sha256:e3b0c442...", "actual": "sha256:e3b0c442..."}
  }
}
```

`entries` is byte-stable: stored files first in sorted path order, then
cleaned files in sorted path order. `workflow_content_check` is `null`
when the checkpoint records no content digest (legacy checkpoints);
`status` is `matched` (file re-hashes to the recorded digest), `changed`
(bytes moved since the run — exit code 1), or `unverifiable` (missing or
unreadable at its recorded path — `actual` omitted, exit code 0).
`workflow_resolved_hash` is the override-aware run-identity fingerprint
described in [Workflow Versioning](../reference/versioning.md). When the
checkpoint has no stored checksums, the document is still emitted with a
`note` field describing the degradation.

## Comparing two checkpoints (`provenance diff`)

`provenance verify` checks **one** checkpoint against the files on disk.
`provenance diff` compares the **recorded** output checksums of **two**
checkpoints — e.g. two runs of the same workflow, or the same workflow on two
hosts. It is the machine-readable primitive for asking whether two runs agree
on every recorded artifact hash, without hand-comparing JSON.

### Usage

```
oxo-flow provenance diff [OPTIONS] <LEFT_CHECKPOINT> <RIGHT_CHECKPOINT>
```

`diff` accepts the same global options as `verify` (`-v/--verbose`,
`--quiet`, `--no-color`, `--json`).

### Output

```
Provenance Diff left/checkpoint.json right/checkpoint.json

  ✓ output/sample1.vcf sha256:abc123...
  ✗ output/report.html (left: sha256:xxx, right: sha256:yyy)
  - output/only_here.txt (only in left)
  + output/new_in_b.txt (only in right)

Summary: 1 matched, 1 differing, 1 only left, 1 only right
```

Each checkpoint's `checksums` and `cleaned_checksums` maps are merged before
comparison via the **same shared merge** (`merge_recorded_checksums`) that
`report --diff` uses, so the two surfaces can never classify the same input
pair differently — a chunk moved into the cleaned bucket is a bookkeeping
change, not a file change, and its merged value carries the `(cleaned by
design)` annotation, so a mixed pair (recorded under `checksums` on one side,
`cleaned_checksums` on the other) reads as `differing`, not a spurious
`matched`. When a checkpoint has no embedded `checksums` object, `diff` falls
back to the same legacy companion `checkpoint.checksums.json` file
`provenance verify` reads. Artifacts are partitioned into four classes:

- `matched` — present in both, identical checksums.
- `differing` — present in both, different checksums.
- `only_left` / `only_right` — recorded on one side only.

### Exit code

`diff` exits **0** when every recorded artifact agrees, and **nonzero** when any
artifact differs or is recorded on only one side — so CI can gate on artifact
agreement directly.

### JSON output

With `--json`, the document is written to stdout (stdout carries nothing else;
the human table stays on stderr):

```
{
  "command": "provenance",
  "diff": {
    "left": "/path/to/left/checkpoint.json",
    "right": "/path/to/right/checkpoint.json",
    "matched": 1,
    "differing": 1,
    "only_left": 1,
    "only_right": 1,
    "entries": [
      {"artifact": "output/sample1.vcf", "status": "matched", "left": "sha256:abc...", "right": "sha256:abc..."},
      {"artifact": "output/report.html", "status": "differing", "left": "sha256:xxx", "right": "sha256:yyy"},
      {"artifact": "output/only_here.txt", "status": "only_left", "left": "sha256:zzz"},
      {"artifact": "output/new_in_b.txt", "status": "only_right", "right": "sha256:www"}
    ]
  }
}
```

`entries` is byte-stable (sorted artifact path order). A missing or malformed
checkpoint is a clear error (nonzero exit), never a panic.

## Portable run attestations (`provenance attest`)

A run's evidence lives in its own `checkpoint.json`. `oxo-flow provenance
attest` binds the recorded pieces into one canonical, portable document —
`oxo-flow.attestation/v1` — that can be handed to another party and,
optionally, signed.

### Usage

```bash
# Unsigned document (JSON on stdout)
oxo-flow provenance attest .oxo-flow/checkpoint.json --json

# Signed, written to a file
openssl rand -hex 32 > attest.key            # or any 32-byte / 64-hex seed
oxo-flow provenance attest .oxo-flow/checkpoint.json \
    --sign --key attest.key -o run.attestation.json

# Verify (exit 0 valid, 2 invalid signature, 3 key mismatch, 4 malformed)
oxo-flow provenance attest-verify run.attestation.json --key attest.key --json
```

`CHECKPOINT` may be a checkpoint file or a run workdir containing
`checkpoint.json` / `.oxo-flow/checkpoint.json`.

### What the document binds

- `workflow`: path, git HEAD SHA, dirty marker, raw content digest, the
  override-aware resolved fingerprint (#1350), and the canonical metadata
  digest of the typed cohort table when one was consumed (#1368)
- `includes`: recorded include checkout SHAs (repo@ref → HEAD)
- `config`: the resolved config snapshot; sensitive values are already
  SHA-256 digests in the checkpoint, never plaintext
- `inputs`: recorded input manifests (`rule:path` → hash, or size/mtime
  fallback for large/legacy files)
- `outputs` / `cleaned_outputs`: recorded per-artifact SHA-256 checksums,
  with intentionally cleaned temporary outputs kept separate
- `environment`: recorded environment identity map
- `outcome`: completed/failed rules and the derived status
- `checkpoint.format_version`

All maps are key-ordered, so emitting twice yields byte-identical output.

### What it does NOT bind

- Biological correctness of any output, or the presence of files on another
  machine.
- Legal or regulatory qualification, and no PKI/key-service identity: a
  valid signature proves *these bytes* were signed by the key that verifies
  it, not who holds that key.

### Signing

Ed25519 over the document with its `signature` field removed; the document
carries `{alg, public_key, signature}` (hex). `--sign` requires an explicit
`--key` file (64 hex characters or 32 raw bytes) — the command never mints
key material silently.

### Exit codes (`attest-verify`)

| Code | Meaning |
| --- | --- |
| 0 | Signature valid, or document unsigned (`signature_status: "unsigned"`) |
| 2 | Signature invalid — the signed bytes changed |
| 3 | Key mismatch — `--key` names a different signer than the document |
| 4 | Malformed/unreadable document, or an unknown format tag |

### JSON output

`--json` prints `{command, file, signature_status, format, workflow_content_hash,
outcome_status}` on stdout; the human report stays on stderr.
