# Comparative benchmarks: oxo-flow vs Nextflow vs Snakemake

> **Status (2026-11-28).** This harness was rebuilt for the measurement
> remediation in issue #1445. The previous numbers in this file are preserved
> below as **historical and invalid for cross-engine comparison**: they timed
> cached Snakemake no-ops and compared oxo-flow `dry-run` against real
> Nextflow/Snakemake execution. The redesigned harness starts every measured
> iteration from a clean state, adds an oxo-flow **real-execution** arm, pins
> the engine versions, and refuses to time an iteration that did not execute
> the workload. Raw `hyperfine` JSON, host/version identity, and a no-op proof
> are committed under [`results/`](results/).

## Workload

All three engines run the same N-step serial chain:

```
input.txt ──> step_0 ──> step_1 ──> ... ──> step_{N-1}
```

Each step executes exactly `echo <i> > step_<i>_output.txt` and consumes the
previous step's output. `step_0` consumes an empty seed `input.txt`. Every
engine runs with one worker (`oxo-flow -j 1`, `snakemake --cores 1`; the
Nextflow chain has a strict dependency between every pair of processes, so it
cannot parallelize).

| Engine | Definition | Depth control |
| :--- | :--- | :--- |
| oxo-flow | generated by `benches/macro/suite.py:generate_hello(N)` | N generated `[[rules]]` |
| Nextflow | generated by `nextflow/generate_nextflow.py` | N static `include` aliases (DSL2 limitation, see below) |
| Snakemake | `snakemake/Snakefile --config count=N` | wildcard rule + input function |

## Arms and what they mean

| Arm | What executes | Comparable to the real arms? |
| :--- | :--- | :--- |
| `oxo-flow run` | parse + DAG + scheduling + **N real process spawns** + checkpoint/log/report bookkeeping | **yes** |
| `oxo-flow dry-run` | parse + DAG + scheduling plan only, **no process spawn** | **no** — scheduling-only arm, kept for engine-internal overhead |
| `nextflow run` | parse + DAG + scheduling + N real process spawns (JVM) | **yes** |
| `snakemake run` | parse + DAG + scheduling + N real process spawns (Python) | **yes** |

The dry-run arm is labeled as such in every table and must never be read as a
real-execution number.

## Fairness contract

- **Fresh state per measured iteration.** `drivers/prepare.sh` (hyperfine
  `--prepare`) deletes every output, checkpoint, and engine metadata directory
  (`.oxo-flow/`, `.snakemake/`, `work/`, `.nextflow/`) and recreates the empty
  seed `input.txt` before each timed run. A measured iteration cannot reuse
  work from a previous one.
- **Non-vacuity guards.** Every timed command (in `drivers/`) counts the
  engine's own execution markers and the produced artifacts, and exits
  non-zero if the full chain did not run. The harness aborts instead of timing
  a partial or cached run.
- **No-op negative control.** Before timing, the harness runs the exact timed
  driver once (must execute and pass) and then a second time in the unchanged
  directory. For oxo-flow and Snakemake the second run does no work, so the
  guard must reject it; the result is recorded in
  `results/comparative-N<N>-proof.txt`. This is the regression proof for the
  original bug: a cached no-op can no longer be measured silently.
- **Pinned engines.** Nextflow is pinned with `NXF_VER` and runs offline
  (`NXF_OFFLINE=true`, no update checks); the installed Snakemake version is
  recorded in the identity file. The oxo-flow binary SHA-256, git commit,
  host/kernel/CPU/memory, and exact command strings are recorded too.
- **Same artifacts.** All engines must produce exactly N
  `step_<i>_output.txt` files (Nextflow publishes them to `results/` with
  `publishDir`; the other two write in place).
- **The guard itself is inside the timed command.** Each real arm ends with a
  log-marker grep and an output count (a few milliseconds), applied to every
  engine identically. `prepare.sh` setup and cleanup are outside the timed
  window.

## What remains asymmetric (documented, not hidden)

- **Runtime startup is inside the measured time.** oxo-flow is a native
  binary; Nextflow pays JVM startup (OpenJDK 21); Snakemake pays Python
  startup. For a microsecond `echo` per step, wall time is dominated by
  engine startup and per-job dispatch, not by the commands. These are
  time-to-process-the-chain numbers, not tool-runtime or data-throughput
  numbers.
- **Bookkeeping differs by engine design.** oxo-flow writes a checkpoint,
  structured log, and report snapshot and verifies outputs; Snakemake writes
  `.snakemake` metadata; Nextflow creates `.nextflow` and per-task work
  directories. All of it is included.
- **Snakemake has one extra zero-shell target.** `rule all` requests the final
  output and counts as one job (no process spawn); the proof records N+1
  finished jobs for N steps.
- **Nextflow output publication copies files.** `publishDir './results',
  mode: 'copy'` makes the produced artifacts comparable to the other engines;
  the copy is part of Nextflow's measured time.
- **Definition form differs.** Nextflow DSL2 allows a given process to be
  called only once per workflow, so the generated definition carries N
  `include` aliases (one per chain position) where Snakemake needs one
  wildcard rule and oxo-flow one generated rule per step. The alias count and
  the definition size are both proportional to N; definition brevity is a real
  engine difference, not a timing trick.
- **Snakemake depth ceiling.** The DAG builder is recursive: chains deeper
  than about 484 steps hit Python's default recursion limit (measured
  previously at 484 OK / 485 fail on Snakemake 9.x). N > 484 is skipped for
  Snakemake and the skip is recorded.
- **Nextflow does not cache a rerun without `-resume`.** The fresh directory is
  still enforced for uniformity; the proof records that a second same-dir run
  re-executes all N processes.

## What these numbers are not

- **Not a general speed claim.** A single host, a single measurement session,
  and a workload of microsecond `echo` commands. No confidence intervals, no
  multi-host replication.
- **Not a bioinformatics benchmark.** No real tools, containers, reference
  data, or I/O payloads are involved; environment activation is excluded.
- **Not directly comparable across N.** The chain is serial, so time grows with
  N by construction.

## Reproduce

Requirements: `hyperfine`, `python3`, a release oxo-flow binary. Nextflow and
Snakemake are optional; when absent they are skipped and the reason is written
to the identity file. For the historical measurement host (`tx-ubuntu`) the
engines were installed in user space (`$HOME/bin/nextflow`,
`$HOME/smk-venv/bin/snakemake`).

```bash
# On the measurement host, with Nextflow/Snakemake on PATH:
cargo build --release -p oxo-flow-cli

PATH=$HOME/bin:$HOME/smk-venv/bin:$PATH \
NXF_VER=26.10.6 NXF_OPTS=-Xmx1g NXF_OFFLINE=true \
HOST_LABEL=tx-ubuntu \
  ./benches/comparative/run_comparison.sh 10 target/release/oxo-flow

PATH=$HOME/bin:$HOME/smk-venv/bin:$PATH \
NXF_VER=26.10.6 NXF_OPTS=-Xmx1g NXF_OFFLINE=true \
HOST_LABEL=tx-ubuntu \
  ./benches/comparative/run_comparison.sh 100 target/release/oxo-flow

# Optional oxo-flow-only scaling point (Snakemake cannot build N > ~484):
PATH=$HOME/bin:$HOME/smk-venv/bin:$PATH \
ENGINES=oxo-flow,oxo-flow-dry-run HOST_LABEL=tx-ubuntu \
  ./benches/comparative/run_comparison.sh 1000 target/release/oxo-flow
```

`make bench-compare` runs the N=10 and N=100 commands above (after the release
build). Useful knobs: `MIN_RUNS` (default 5), `WARMUP` (default 1),
`ENGINES=oxo-flow,oxo-flow-dry-run,nextflow,snakemake`, `RESULT_DIR`,
`KEEP_WORK=1`, `GIT_COMMIT`/`GIT_DIRTY_FILES` (identity for trees without
`.git`). The harness creates a temporary sandbox and removes it on exit; every
path inside it is relative, so the committed JSON contains no host paths.

Each run writes:

- `results/comparative-N<N>.json` — raw `hyperfine` JSON (commands, times,
  median, mean, stddev, min/max);
- `results/comparative-N<N>-identity.txt` — host/kernel/CPU/memory, git
  commit, binary SHA-256, engine versions and pinned env, definition/driver
  hashes, exact command strings;
- `results/comparative-N<N>-proof.txt` — fresh-run execution markers, produced
  artifacts, second-run markers, and whether the timed guard rejected the
  cached rerun.

## No-op proof (the original P0)

The previous runner reused one `SM_RUN_DIR` for every hyperfine iteration.
Hyperfine's warm-up runs created all Snakemake outputs, so every measured run
printed `Nothing to be done` and executed zero jobs; the ~1.0 s numbers were
Snakemake startup only. The same runner timed `oxo-flow dry-run` while the
other engines executed.

The new proof file records, for the exact timed drivers:

```
engine | fresh_markers | fresh_outputs | second_same_dir_markers | guard_on_cached_rerun
oxo-flow | <N> rule_started | <N> outputs | 0 rule_started | rejected (exit != 0)
snakemake | <N+1> Finished job | <N> outputs | 0 Finished job | rejected (exit != 0)
nextflow | <N> Submitted process | <N> outputs | <N> Submitted process | n/a (re-executes without -resume)
```

A second run in the unchanged directory is a cached no-op for oxo-flow and
Snakemake, and the timed guard rejects it; the measured commands always run
after `drivers/prepare.sh`, so every timed iteration is a fresh, full
execution.

## Results (tx-ubuntu, 2026-11-28)

**Identity.** Linux 6.8.0-137 x86_64 (Ubuntu 24.04), Intel Xeon Platinum 8255C,
4 vCPU, 3.6 GiB RAM (a shared VM that also runs an idle k3s control plane).
oxo-flow 0.32.0 built from commit `4d5399d5` (release profile, binary SHA-256
`b7464e08…64574b`); Nextflow 26.10.6 on OpenJDK 21.0.11 with
`NXF_OPTS=-Xmx1g` and `NXF_OFFLINE=true`; Snakemake 9.27.2 on Python 3.12.3;
hyperfine 1.18.0; warm-up 1, minimum 5 timed runs. Exact files:
[`results/comparative-N10-identity.txt`](results/comparative-N10-identity.txt)
and
[`results/comparative-N100-identity.txt`](results/comparative-N100-identity.txt).

Every timed iteration ran after `drivers/prepare.sh` and passed its
non-vacuity guard. `n` is the number of timed runs hyperfine selected: the
minimum is 5, and faster arms run more to fill hyperfine's minimum
benchmarking time. N=10 and N=100 cover all three engines; N=1000 is the
optional oxo-flow-only scaling point (see below).

| Arm | median | mean ± σ | n |
| :--- | ---: | ---: | ---: |

This point is oxo-flow-only by scope: the harness skips Snakemake above ~484

~1.27 s. Per-rule

plan stays at 175 ms, so the growth is in per-rule execution/bookkeeping, not

identity:

### Execution evidence

The proof files show a fresh run executing the whole chain, and the immediate
second run in the unchanged directory doing zero work for the two engines that
cache — rejected by the timed guard:

| Engine | fresh run | fresh outputs | immediate rerun | guard on rerun |
| :--- | :--- | ---: | :--- | :--- |
| oxo-flow | N `rule_started` | N | 0 `rule_started` | rejected |
| Snakemake | N+1 `Finished job` | N | 0 jobs (`Nothing to be done`) | rejected |
| Nextflow | N `Submitted process` | N | N (no implicit resume) | n/a |

### Reading the numbers

- **Runtime startup dominates the real arms.** Each step is a microsecond
  `echo`; the workload contributes almost no tool time. Nextflow's JVM startup
  and Snakemake's Python startup are a large share of their wall times;
  oxo-flow's native startup is small, but its per-rule process spawn and
  per-run bookkeeping are visible as N grows.
- **oxo-flow real growth:** 217 ms at N=10 → 1.758 s at N=100 → 86.26 s at
  N=1000. The N=100 run spent 1.27 s of system time (mean), i.e. spawning one
  shell per rule and the per-run checkpoint/report work, not DAG computation.
  The N=1000 median is ~49× the N=100 median for 10× the rules; the dry-run
  plan at the same size stays at 175 ms, so the increase is per-rule
  execution/bookkeeping cost, not parse or DAG cost.
- **Nextflow real:** 4.26 s → 7.49 s; **Snakemake real:** 2.04 s → 3.01 s.
  Their growth over N reflects per-job dispatch on top of interpreter/JVM
  startup.
- **The dry-run column is not real execution.** At N=100 oxo-flow's dry-run is
  ~74× faster than its own real run (24 ms vs 1.76 s). It measures parse +
  DAG + scheduling only and must not be compared to the other engines' real
  arms.
- No general speed advantage is claimed. One host, one measurement session,
  microsecond commands, no containers/tools/data; see the caveats above.

## Engine semantic differences that shape the definitions

- **Nextflow (DSL2):** *"A given process or workflow can only be called once
  in a given workflow"* (docs.seqera.io/nextflow/dsl2). A serial chain must
  reuse one process N times, so the generated `hello.nf` carries **N static
  include aliases** plus N one-line calls (about 2 lines per step; the
  Snakefile is 43 lines at any N).
- **Snakemake:** dynamic chains of any depth via a wildcard rule and an input
  function, but the DAG builder is recursive; chains deeper than ~484 steps
  hit Python's default recursion limit.
- **oxo-flow:** generated `[[rules]]`; no per-step definition cost and no
  expression-level depth limit in this range.

## Residuals (2026-11-28 measurement)

- **Single host, single session.** `tx-ubuntu` only; no cross-host, cross-day,
  or repeated-session replication. Hyperfine reports a median over its selected
  runs, not a confidence interval over independent sessions.
- **Microsecond workload only.** No tools, containers, data, or I/O payloads;
  environment activation is excluded. These numbers say nothing about
  bioinformatics throughput.
- **Engine startup is inside the numbers.** JVM (Nextflow), Python
  (Snakemake), and native (oxo-flow) startup are measured, because time to
  process the chain includes them.
- **N=1000 is oxo-flow-only.** The harness skips Snakemake above ~484 steps;
  the optional 1000-rule point is an oxo-flow scaling check, not a cross-engine
  comparison.
- **The host is a shared VM.** It also runs an idle k3s control plane; no CPU
  pinning or cgroup isolation was applied.
- **Superlinear per-rule cost at N=1000 (observation, not diagnosed).** The
  oxo-flow real arm's per-rule wall time rises from ~17.6 ms at N=100 to
  ~86 ms at N=1000 while the dry-run plan stays at 175 ms. This layer records
  the measurement; it does not diagnose or fix the cost. A plausible candidate
  is per-completion checkpoint/report bookkeeping whose size grows with the
  rule count, but that was not instrumented here.
