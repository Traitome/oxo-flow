# Release Process

This document describes the release process for oxo-flow.

## Version Numbering

oxo-flow follows [Semantic Versioning 2.0.0](https://semver.org/):

- **MAJOR** (`X.0.0`) — Incompatible API changes or breaking changes to the
  `.oxoflow` file format.
- **MINOR** (`0.X.0`) — New features and functionality added in a
  backwards-compatible manner.
- **PATCH** (`0.0.X`) — Backwards-compatible bug fixes and security patches.

### Pre-release Versions

Pre-release versions use suffixes: `1.0.0-alpha.1`, `1.0.0-beta.1`,
`1.0.0-rc.1`.

### Version Locations

The version is maintained in:

- `Cargo.toml` (workspace root) — the `[workspace.package]` version plus the
  `oxo-flow-*` entries under `[workspace.dependencies]`; every member crate
  inherits via `version.workspace = true`
- `CITATION.cff`
- `docs/guide/src/**` + `README.md` (release-notes references)
- `crates/oxo-flow-desktop/Cargo.toml` — standalone crate outside the
  workspace; repeats the version twice (own `[package]` version + the
  `oxo-flow-web` path-dependency pin) and carries its own `Cargo.lock`
- `frontend/package.json` (+ `package-lock.json`) — ships inside the
  desktop app bundle

None of these need manual edits for a release: the CI `sync-version` job
patches them all from the tag and commits the bump (see Publishing Steps).
Only edit them by hand for a mid-cycle correction.

## Release Checklist

Before creating a release, ensure the following:

- [ ] All CI checks pass on the `main` branch
- [ ] `cargo fmt -- --check` reports no formatting issues
- [ ] `cargo clippy -- -D warnings` reports zero warnings
- [ ] `cargo build` succeeds for all workspace members
- [ ] `cargo test` passes all unit and integration tests
- [ ] **Knowledge freshness gate**: the embedded AI knowledge data
      (`crates/oxo-flow-ai/src/knowledge/`) must be ≤ 60 days old —
      `sync-version` hard-fails otherwise. If tripped, run the
      Knowledge Refresh workflow first, merge its PR, then re-dispatch
- [ ] `CHANGELOG.md` will be regenerated by CI (git-cliff) — verify the
      preview (`git-cliff --config cliff.toml --current`) covers the release
- [ ] Documentation is updated to reflect any new features or changes
- [ ] Breaking changes are clearly documented with migration instructions
- [ ] Security advisories for resolved vulnerabilities are prepared (if any)

## Changelog Generation

oxo-flow uses [git-cliff](https://github.com/orhun/git-cliff) for automated
changelog generation. Configuration is in `cliff.toml`.

### Commit Message Convention

Follow [Conventional Commits](https://www.conventionalcommits.org/):

```
<type>(<scope>): <description>

[optional body]

[optional footer(s)]
```

Types: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`,
`ci`, `chore`.

### Generating the Changelog

```bash
# Preview the changelog for the next release
git-cliff --config cliff.toml --current

# Generate the full changelog locally (CI does this at release time)
git-cliff --config cliff.toml --output CHANGELOG.md
```

## Publishing Steps

The primary release path is **workflow dispatch** — CI derives every version
reference from the tag, commits the bump, regenerates the changelog, then
creates and pushes the tag. No manual version edits.

### 1. Prepare the Release

```bash
# Ensure you are on the main branch and up to date
git checkout main
git pull origin main

# Run the full CI suite locally
make ci

# Optional: preview the release notes git-cliff will generate
git-cliff --config cliff.toml --current
```

### 2. Dispatch the Release

```bash
gh workflow run ci.yml -f tag=vX.Y.Z
```

The `sync-version` job then:

1. validates the tag format (`vX.Y.Z`) and that it does not already exist,
2. enforces the knowledge-freshness gate (see checklist above),
3. patches every version location (workspace + desktop crate + frontend +
   `CITATION.cff` + docs) and runs `cargo update --workspace` in both
   lockfiles,
4. commits the bump to `main`, regenerates `CHANGELOG.md`, and creates and
   pushes the tag against the changelog commit.

The release pipeline then builds and uploads all platform binaries plus the
desktop artifacts (macOS `.app` zip + `.dmg`, Linux `.deb`/`.rpm`/`.AppImage`,
SHA256 checksums), publishes the workspace crates to crates.io in dependency
order, and attaches the git-cliff release notes.

A tag push (`git tag -a vX.Y.Z ... && git push origin vX.Y.Z`) still works as
a fallback — `sync-version` re-points the tag to the version-bump commit so
`publish-crates` sees the synced tree.

> **Known gotcha:** GitHub does not always deliver tag-push events to
> Actions. If the release pipeline does not start within a few minutes of
> the tag push, run it manually with
> `gh workflow run ci.yml -f tag=vX.Y.Z` (workflow_dispatch), which takes
> the same tag parameter and produces the same assets.

### 3. Verify the GitHub Release

Check the [Releases page](https://github.com/Traitome/oxo-flow/releases):
all platform assets present, release notes match the changelog section,
and the crates.io publish job succeeded.

### 4. Post-Release

- Announce the release on project communication channels
- Update documentation site if applicable
- Verify the published crates on [crates.io](https://crates.io/)

No development-version bump is needed afterwards: `main` stays at the
released version until the next dispatch, and `sync-version` syncs it then.

## Hotfix Releases

For urgent bug fixes or security patches:

1. Create a branch from the release tag: `git checkout -b hotfix/vX.Y.Z vX.Y.Z`
2. Apply the fix and add tests
3. Follow the standard release process from step 2 onward (the dispatch
   fallback applies to hotfix tags too)
